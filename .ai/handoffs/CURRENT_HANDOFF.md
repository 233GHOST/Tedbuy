**UPDATE — RLS migration design complete (read-only, no implementation).** `.ai/handoffs/SUPABASE_RLS_MIGRATION_PLAN.md` (new document). Requested as the next step after the sweep closed: design the safe path from `Web → dbAdapter → Supabase anon key` to `Web → Firebase Auth → authenticated TedBuy server API → server-side Supabase`, without touching RLS, policies, grants, schema, `dbAdapter.ts`, `server.ts`, or client code. Nothing was implemented — this is a design document only.

**Headline finding, not fixed (per this task's explicit no-implementation instruction):** building the read/write inventory surfaced a live, unauthenticated bulk PII exposure not covered by the completed sweep — `AppContext.tsx`'s `fetchUsersOnce` reads the **entire `users` table** directly from Supabase (`select('*')`, no auth, no column restriction), returning every user's email/phone/WhatsApp number/admin-status/suspension-status to anyone. A safe, purpose-built replacement already exists and is unused by web (`GET /api/users/list`, built for mobile, already strips PII). Flagged prominently in the plan (§0) as P0/P1-equivalent severity — recommend authorizing this as a fast, standalone fix rather than letting it sit through the full migration timeline, since it's a one-line call-site swap onto an endpoint that already exists.

**Core architectural finding:** confirmed via exhaustive grep that TedBuy has **no Supabase Auth session anywhere** — the browser only ever authenticates to Firebase, never to Supabase (`createClient(url, anonKey)` with zero `.auth.signIn*` calls found). This means `auth.uid()` in any RLS policy is always `NULL` for every browser request; no RLS policy can express per-user ownership without inventing a Firebase→Supabase JWT bridge (explicitly not proposed, per instruction — none currently exists). Consequence: the target RLS design is deliberately simple — default-deny on every table, zero policies, once all legitimate traffic is moved off the anon key entirely. RLS's only real job in this architecture is capping what the public anon key can do; per-user authorization remains, and must remain, the server's job.

**What the plan contains:** a full per-table inventory (10 tables, every read/write operation, current caller, current authorization, sensitivity, category A/B/C/D, existing-vs-new endpoint mapping, what breaks if RLS flips on today, priority); confirmation that most of the necessary secure server endpoints **already exist** and are simply unused by web (`/api/users/list`, `GET /api/reviews`, partial `/api/users/sync` coverage) — the same "infrastructure already exists, web wasn't migrated" pattern found repeatedly throughout the completed sweep; a 6-phase rollout (0: close remaining dangerous direct access — 1: protected writes — 2: protected reads — 3: confirm nothing needs to stay public via the anon key — 4: enable RLS, default-deny — 5: verification matrix across anonymous/normal/cross-user/admin identities); an explicit list of what breaks in production if RLS were flipped on today with no migration (registration, profile save, save/unsave a listing, likes/views, the user directory, admin support-desk inbox, message read-state); and a rollback strategy (RLS is a pure gate, not a data/schema change — `DISABLE ROW LEVEL SECURITY` is instant and safe if Phase 4 surfaces something Phase 5's verification missed).

**Recommendation:** the browser should end this migration talking to Supabase for nothing at all — `dbAdapter.ts`'s Supabase branch becomes dead code, not a smaller allow-list. Even the genuinely-public content (`products`, `reviews`) should stay server-mediated rather than gain an RLS-protected anon-read policy, because the existing server endpoints already do more (moderation filtering, caching) than a raw table grant would.

**Status unchanged: BLOCKED_APPROVAL.** No RLS, policy, grant, schema, `dbAdapter.ts`, `server.ts`, or client-code changes made in this pass. Waiting on Vincent's review of the plan and an explicit go-ahead before any implementation phase begins — including Phase 0, which touches client code even though it's framed as "prerequisite."

Four more real, distinct vulnerabilities found and fixed this pass, plus one prior audit-doc error corrected:

- **(P1) Username-quarantine bypass** (§20): the 90-day quarantine applied on account deletion (`store_names.status = 'quarantined'`) was written but never actually enforced at the real username-claim path (`/api/users/sync`) — only read by a pure UI-hint endpoint. A user could claim a just-deleted user's exact username (and its reputation) immediately. Fixed with a real server-side check; direct-Supabase route closed too (`status`/`availableAfter`/`quarantinedAt` stripped from `dbAdapter.ts`'s allow-list — no legitimate client write ever needed them).
- **(P1) Ranking manipulation via `/api/products/sync`** (§21.1): `viewsCount`/`likesCount`/`likedUserIds` were trusted as absolute client-supplied values, reachable against **any** listing (not just your own) via an intentional ownership-check bypass built for legitimate liking/viewing of someone else's listing. Both feed directly into ranking (`engagementScore`/`priorityScore`). Fixed: likes now only ever toggle the calling user's own id, the count is always derived from that array, views are preserved from the existing row unconditionally (no legitimate caller needs an absolute value here).
- **(P1) `reports` table completely unfiltered** (§21.2): missing from `dbAdapter.ts`'s `TABLE_COLUMNS` entirely (every other table has an entry) — a genuine oversight, not a deliberate gap, and it corrects an earlier (wrong) claim in this document's own §2 that assumed a missing entry caused a safe no-op. It didn't — writes passed through completely unfiltered. `reportProduct()` also spoofable client-side (`reporterId` from local state). Fixed by migrating to the already-existing, already-correct `POST /api/reports/create`, plus full write-barriers in `dbAdapter.ts`.
- **(P2) `reviews` write-then-null gap** (§21.3): no direct-write caller remained after an earlier pass's migration to `/api/reviews/create`, but a bare `setDoc(doc('reviews', id), {})` could still null an existing review by id. Closed with the same write-barriers as `reports`.
- **(Hardening) `emailVerified` client-trust in `/api/users/sync`** (§19): now derived from Firebase Admin SDK's own record instead of trusted from the client body — unlike `isAdmin`/`isSuspended`, simply preserving the existing DB value would have broken the legitimate "just verified my email" transition, so a different fix shape was needed here.

**Explicitly documented, not fixed** (§22) — same RLS-dependent residual-risk bucket as the rest of this document, each requiring new endpoint infrastructure or a product decision beyond an unambiguous fix-in-place: `viewsCount`/`likesCount`/`likedUserIds` remain writable via the direct-Supabase route (`toggleLikeProduct`/`incrementProductViews` depend on it, including anonymous view-tracking — `dbAdapter`'s `increment()` helper was confirmed to provide no real server-side atomicity, purely a client-side convention); `notificationPreferences` has no per-row ownership check on the generic write path (low severity — a muting/griefing nuisance, not privilege/money/identity); a `sellerVerified` display bug was found (`|| true` makes the "verified seller" badge unconditionally true for every seller) but is a business-logic anomaly with zero client input involved, out of this audit's scope, not fixed.

**UPDATE — notification security layer BUILT, revising the previous "not fixed" assessment.** `.ai/handoffs/SUPABASE_DIRECT_ACCESS_AUDIT.md` §18.

§17 said closing notifications properly required building new server infrastructure and deferred it. Actually building it turned up something important: **most of the server infrastructure already existed** — `GET /api/notifications`, `POST /api/notifications/{mark-read,mark-all-read,clear-all}`, and `POST /api/users/follow` were already correctly built (real `verifyUser()` auth, real `.eq('userId', verified.uid)` ownership scoping) and **mobile already used all of them**. Web just never adopted them and kept using the old insecure direct-Supabase path in parallel. So this was substantially a migration task, not a from-scratch build:

- **Migrated**: web's notification read (was a live Supabase Realtime subscription with no server-side identity check on its own filter — now a 20s poll of the real, authenticated endpoint; real UX tradeoff, no more instant push, documented as deliberate), mark-read/mark-all-read/clear-all, and follow/unfollow — all now call the real server endpoints instead of writing directly.
- **Removed as redundant**: `sendMessage`'s and `createProduct`'s own direct notification broadcasts — both already had an equivalent, real, server-authoritative notification firing automatically via `/api/messages/send`/`/api/products/sync`, so the client-side versions were duplicating (insecurely) work the server already did correctly.
- **Genuinely built new**: server-side "listing updated" notifications (no prior equivalent existed — added to `/api/products/sync`, mirroring its own existing new-listing notification pattern exactly), and a narrow admin-only fallback in `/api/messages/send` so an admin can reply as the CEO-support pseudo-account server-side (`verified.isAdmin`-gated, never client-claimed) — this was the one case with no existing endpoint, and building it was what allowed **fully** closing the vulnerability rather than leaving one insecure exception open.
- **Closed for good**: `dbAdapter.ts` no longer maps `'notifications'` to anything at all — not just an emptied allow-list, the table mapping itself is gone, so there's no direct-Supabase route left for anyone to use, confirmed by a repo-wide grep finding zero remaining client-side notification writes.
- Every notification type traced had an unambiguous, checkable server-side event to verify (follow → real followingSellers check; message → real chat-participant check; listing new/updated → real ownership + follower/saved-user data; admin-support → real cryptographic admin check) — nothing was invented or guessed at.

**Testing**: 13 rejection-path tests executed live (all pass) plus a static confirmation the direct-Supabase route is gone; `tsc`/build clean. Explicitly did NOT fabricate the identity-dependent tests requested (two real accounts, a real admin, a real non-admin) — no test-credential infrastructure exists for that here, and it's flagged plainly rather than faked.

Classified P1 (real impersonation/privacy risk, not financial/account-takeover). Documented with a concrete recommended build order (mark-read/delete endpoints first — simple ownership checks, low risk; creation endpoint with per-type validation second) rather than guessed at or rushed. **Five P0/P1 vulnerabilities closed this session total, all fixed, tested to the extent safely possible, and committed.** Full detail: `.ai/handoffs/SUPABASE_DIRECT_ACCESS_AUDIT.md` §13-16.

- **Free, unlimited boost activation** — `server.ts`'s `upsertProductToSupabase()`, called by `/api/products/sync` (the ordinary "save my listing" endpoint every seller already uses), trusted `boostStatus`/`boostExpiry` straight from the client request body. Confirmed these are exactly the fields the real ranking computation (`getServerBoostEndDate()`) reads to decide whether a listing is actively boosted. **Any seller could grant themselves a free, arbitrarily-long, ranking-relevant boost via one ordinary API call — no payment, and no RLS bypass needed at all**, since this endpoint already runs through the service-role Supabase client. - **Unlimited payment-reference replay** — `/api/verify-payment` never checked whether a `paymentReference` had already been used. Since Paystack's verify endpoint is idempotent (reports "success" forever for a real past transaction), one payment could be replayed to indefinitely extend the same boost or activate boosts on multiple listings. A `boost_purchases` table already existed in the schema for exactly this purpose but nothing ever wrote to it.
- **Direct-Supabase route was open too** (defense-in-depth) — same boost fields were also in `dbAdapter.ts`'s client write-allowlist; closed the same way as every prior fix this session.

- Confirmed safe (no fix needed): a client can't inflate the boost amount (server/Paystack-derived), can't boost someone else's listing (ownership-checked), and can't bypass expiry (recomputed fresh from stored dates on every read, no tamperable flag).
- The Paystack-secret-missing fallback ("demo mode") was re-inspected: deterministic, per-request, unreachable in production given the key is confirmed configured — the new replay protection also now applies to that branch regardless.
