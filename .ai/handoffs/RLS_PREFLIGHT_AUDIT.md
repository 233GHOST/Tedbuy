# RLS Pre-Flight Audit (post service_role migration)

**Read-only.** No schema changes, no RLS, no policies, no grant changes. This re-audits the current production architecture now that `backendSupabase` is confirmed running on a real `service_role` key (commit `4c1d667`, confirmed live via Render's deploy log). Everything below is a fresh check against current code — not a restatement of earlier session memory — including correcting two errors an automated first pass produced (caught by manual verification before they made it into this document).

**Method note:** table-to-endpoint mapping was built by scanning `server.ts` for every `.from('<table>')`/`safeBackendSupabaseUpsert('<table>'` call and correlating it to the nearest preceding route declaration — first pass missed 4 indented/nested route declarations (`/api/auth/delete-account` and neighbors), which misattributed several tables to `/api/auth/verify-admin-pin`. Corrected using the complete, indentation-independent route list before producing the table below. Auth-requirement detection was similarly corrected from a loose whole-handler scan (which produced false positives, e.g. flagging the public `/api/products/:productId` and `/api/users/get` as admin-gated) to a tight early-gate check, then cross-checked by hand for anything still surprising — this caught that `/api/admin/accounts/security-hold`, `/api/admin/users/suspend`, and `/api/admin/users/delete` use an inline `verifyUser()` + manual `isAdmin` check rather than the `verifyAdmin()` helper; confirmed by direct read that all three are correctly admin-gated, just via a different code pattern than the automated scan was looking for.

## Cross-cutting confirmations

**Server consistently on `service_role`**: confirmed — exactly one `createClient()` call in `server.ts` (`backendSupabase`, 211 references throughout the file, all sharing the one client). Live production log already confirmed `role: service_role`, no warning. RLS with zero policies genuinely has no effect on any server-side operation now.

**Mobile has no direct Supabase dependency**: confirmed — zero occurrences of `supabase`/`Supabase` in any `mobile/src/` import or SDK call; the four text matches found are all comments explaining that mobile calls the (Supabase-backed) server API, not the SDK itself. Mobile's only direct-database dependency is Firestore (`chats`/`messages`/`chat_typing`), a separate system already investigated (the hardcoded bypass secret in `firestore.rules`, fixed and confirmed dead against the live database).

**Residuals re-checked**:
- `emailVerified` — still always Firebase-Admin-SDK-derived server-side (`fbUser.emailVerified === true`), never trusted from a client body. Unchanged, confirmed clean.
- `viewsCount`/`likesCount`/`likedUserIds` — see the `products` row above. No live write path; the client allow-list is broader than strictly needed but not currently exploitable via the app's own code, and would be fully closed by RLS regardless.
- `notificationPreferences` — confirmed already removed from `dbAdapter.ts`'s `users` allow-list entirely (Phase 0 checkpoint 4); no residual at all.
- `reports` — table now exists, correct grants confirmed, feature confirmed working end-to-end in production today.

**Grants don't complicate the RLS decision**: `anon`/`authenticated` still hold their original `GRANT ALL` on every pre-existing table (from `supabase_schema.sql`, never revoked). This is not a blocker — once RLS is enabled with zero policies, Postgres evaluates RLS as an additional gate on top of grants; zero policies means zero visible rows/writable rows for any role without `BYPASSRLS`, regardless of what's granted. The existing grants become inert for `anon`/`authenticated` the moment RLS turns on; only `service_role`'s `BYPASSRLS` attribute keeps working.
